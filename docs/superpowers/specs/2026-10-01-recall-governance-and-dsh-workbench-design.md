# amem 召回治理与 DSH 记忆工作台

日期：2026-10-01  
状态：已确认，待实施计划  
范围：L2 召回门控、会话冻结 Hot Memory、冲突人工裁决，以及 DSH Web 面板的列表、审阅与视觉重构。

## 1. 目标

amem 已具备证据约束、信任等级、分层存储与 L3 人工晋升；本轮补齐“已检索的记忆如何被使用”的治理与可见性：

1. 将“检索”与“注入”分开，每条候选先得到可审计的使用决定。
2. 在同一会话内冻结首次自动装配的记忆，保持 prompt 前缀稳定。
3. 冲突记忆不再自动注入；用户可在 DSH 面板中对比、裁决和追溯。
4. 将当前简陋的六 Tab 列表升级为紧凑、可筛选、分页、可审阅的 DSH 原生工作台。

## 2. 非目标

- 不实现图数据库、实体关系检索或新的 embedding 后端。
- 不把 workspace 变成记忆的主分区键；情境召回仍是核心。
- 不自动写入 L3，不放宽现有人工合并门槛。
- 不使用 DSH 私有事件、DOM 注入或浏览器 hack 自动写 system prompt。
- 不实现跨宿主历史导入、负知识账本或自动 handoff；它们是后续独立范围。
- 不引入 UI 组件库、CSS 框架或外部运行时依赖。

## 3. 召回门控

### 3.1 职责边界

现有 `recall()` 只负责按情境找回并排序候选。新增 `decideRecall()` 作为纯决策层：它接收排序候选及配置，输出每条记忆的 `use`、`verify` 或 `ignore` 决定和机器可读理由。

门控不修改 `MemoryRecord`，不修改排序分数，也不做新的模型调用。决策依据限定为：

- 记忆状态和有效期；
- T1/T2/T3 信任等级；
- 召回分数；
- helpful/harmful 统计；
- 当前模式与预算。

`conflict`、`frozen`、`expired`、`superseded` 永远为 `ignore`，不允许自动注入。它们仍可由人工检索、详情页和冲突审阅查看。

### 3.2 模式

`amem.toml` 的 recall 配置扩展为：

| 模式 | 行为 |
|---|---|
| `shadow` | 运行检索和门控，记录审计，Context Pack 零记忆注入。 |
| `assist`（默认） | 注入 `use`；`verify` 以明确“待核验线索”形式、受较小预算进入 Pack。 |
| `enforce` | 仅注入 `use`，省略 `verify`。 |

当最近门控决策的反馈样本数达到配置的最低值，且 harmful 比例达到阈值时，系统自动将有效模式降为 `shadow`。自动降级必须写审计记录；恢复只能由用户在配置或审阅页明确操作。

### 3.3 反馈关联

每次 `ContextPack` 中的注入项目保留决定和记忆引用。既有 `memory_feedback` 继续更新记忆统计；门控审计额外记录其结果，以便计算健康状态。模型自评不构成 helpful 信号，也不能触发模式恢复。

## 4. 会话冻结 Hot Memory

### 4.1 规则

会话第一次请求自动 Context Pack 时：

1. 运行 recall 与 `decideRecall()`；
2. 按模式和预算生成 Pack；
3. 保存可渲染的注入文本、每条决定、预算用量和配置指纹；
4. 将该 Pack 标记为该会话的冻结快照。

同一 session 后续自动装配复用快照，不因新记忆、反馈或索引重建而改变前缀。新写入的记忆仍可通过显式 `memory_recall` 查询，但不会改变已冻结的自动注入文本。新 session 建立新的快照。

### 4.2 存储与恢复

冻结快照和门控审计写入 `manifests/`，是由 Markdown 记忆与当时配置派生的审计产物，而不是第四层真相源。进程重启后按 session id 从 manifests 读取最近有效快照；缺失、损坏或配置不兼容时明确记录降级原因并重新生成。

面板可显示：

- 当前 session 的冻结快照、预算和决定；
- 以当前记忆状态计算的“下一会话预览”；
- 两者之间新增、移除或改变决定的条目。

## 5. 冲突裁决

### 5.1 裁决动作

冲突在进入审阅前保持 `conflict`，且不自动注入。审阅页展示两条记忆的标题、种类、层级、信任、正文、证据、更新时间和统计，并提供：

| 动作 | 写入结果 |
|---|---|
| 保留 A | A 设为 `active`；B 设为 `superseded`，其 `supersedes` 指向 A。 |
| 保留 B | B 设为 `active`；A 设为 `superseded`，其 `supersedes` 指向 B。 |
| 并存 | A、B 都设为 `active`；审计记录为人工确认并存。 |

裁决记录写入 manifest/audit，包含操作者、输入 id、动作、双方更新前的 `updated_at` 和结果。记忆 Markdown 仍是状态和关系的唯一真实来源。

### 5.2 并发和失败

裁决请求带双方加载时的 `updated_at`。服务端写入前重读：任一时间戳不一致即返回 409，前端提示刷新；不得静默覆盖人类编辑。

裁决跨两份 Markdown 文件，不能假设单文件 rename 可以提供跨文件原子性。服务端必须先在 `manifests/transactions/` 写入包含操作前文本、目标文本和状态的事务日志，再写两份目标文件；成功后更新索引、写审计并删除事务日志。写入失败时用日志恢复已改文件。启动和每次裁决前先恢复遗留事务；恢复失败时返回 500、保留日志并停止该次裁决。事务日志是恢复材料，不是记忆真相源。

### 5.3 审阅 API

- `GET /amem-api/review` 返回冲突对、近期门控决定和当前/下一会话快照摘要。
- `POST /amem-api/conflicts/:leftId/resolve` 接受 `{ rightId, action, leftUpdatedAt, rightUpdatedAt }`；`action` 只能为 `keep_left`、`keep_right` 或 `keep_both`。
- 未知记忆返回 404；两个记忆不构成当前冲突对、非法动作或非法时间戳返回 400；版本冲突返回 409。

## 6. DSH 集成边界

本轮核心提供稳定的门控、冻结和 `context_pack` 契约。DSH Adapter 继续采集会话和暴露管理 API。

当前工程尚未验证 DSH 的稳定自动 system-prompt 注入接缝。因此第一期不启用 DSH 自动注入，只通过 MCP/显式 Context Pack 使用门控结果。待以官方 API 或实测验证宿主接缝后，才在 Adapter 内加入受 feature flag 控制的自动注入；不使用私有事件、DOM 操作或不稳定接口。

## 7. 列表 API、过滤与分页

### 7.1 记忆 API

`GET /amem-api/memories` 接受：

- `page`：正整数，默认 `1`；
- `pageSize`：`20`、`50` 或 `100`，默认 `20`；
- `q`：可选标题、适用情境和正文关键词；
- `kind`、`level`、`trust`、`status`：可选枚举过滤条件。

返回：

```ts
{
  items: MemoryListItem[];
  total: number;
  page: number;
  pageSize: number;
  facets: {
    kind: Record<MemoryKind, number>;
    level: Record<ScopeLevel, number>;
    trust: Record<Trust, number>;
    status: Record<MemoryStatus, number>;
  };
}
```

过滤、排序（`updated_at` 倒序）和切片必须在服务端完成。第一期以 `MemoryStore.listAll()` 的 Markdown 真相源为基础实现；不得为了列表功能引入第二份数据源。后续可将同一契约优化为索引 SQL 查询。

非法枚举、非正页码、非允许的 pageSize 返回 400。超出总页数的合法 page 返回空 `items`，保留正确的 `total` 和 `facets`。

### 7.2 能力与提案

能力和提案复用 `page`、`pageSize`、`q` 及统一分页响应形状。它们不展示无意义的记忆维度筛选器。现有 API 的调用方在迁移期兼容默认分页响应。

## 8. DSH 面板信息架构与视觉

### 8.1 布局

面板改为紧凑工作台：

- 顶部显示 amem 标识、当前视图标题与已加载的摘要计数（总记忆、冲突、提案）。
- 宽屏采用左侧窄导航，按“记忆资产”（记忆、能力、提案、审阅）和“系统”（运维、配置、说明）分组。
- 窄屏降级为可横向滚动的 Tab 导航，保持所有原有入口可达。
- 使用 DSH 宿主颜色、系统字体、清晰边框和有限圆角；禁止渐变、大阴影和装饰性卡片网格。

### 8.2 记忆列表

工具栏依次为搜索、分类、层级、信任、状态过滤器和清除筛选。筛选条件、搜索词或 pageSize 改变时，页码重置为 1。

每行记忆显示标题、状态 badge、种类/层级/信任、适用情境、两行内正文预览、更新时间和遗忘操作。状态必须有文字，不可只用颜色。无结果时说明筛选结果为零并提供“清除筛选”。底部显示总数、页码、上一页/下一页和 pageSize 选择。

### 8.3 审阅、运维与配置

“审阅”视图聚合冲突记忆、近期门控决定和会话快照预览。冲突以左右并排的可比较视图呈现，裁决按钮需二次确认。

运维结果默认渲染状态、关键计数和摘要，原始 JSON 收进 `<details>`。配置表单改为有说明的分区和固定的保存操作区，但保持现有 API Key、privacy、embedding 的安全限制。

客户端拆分数据请求、列表、分页、过滤器、记忆行、审阅和表单展示组件；避免继续扩张单一 `panel.tsx`。

## 9. 验收与测试

1. 管理层测试验证 kind/level/trust/status/q 组合过滤、facet 计数、排序、页边界与非法查询。
2. 门控测试覆盖三种模式、状态硬拒绝、`use/verify/ignore` 结果、预算截断与 harmful 自动降级。
3. 快照测试覆盖首次创建、同会话稳定、进程重启复用、损坏快照降级与新 session 重建。
4. 冲突测试覆盖三种裁决、写前版本冲突 409、失败原子性和审计内容。
5. DSH 路由测试覆盖新列表参数、审阅端点、400/404/409 映射、遗留事务恢复和现有鉴权。
6. UI 测试或可验证渲染覆盖筛选重置页码、翻页、空态、错误态、禁用态和键盘访问；人工检查 320px、768px、1024px 宽度。
7. 回归运行 core、retrieval、store、adapter-dsh 和 amem-dsh-ui 的现有测试与构建。

## 10. 实施顺序

1. 核心类型、配置、门控决定和快照审计。
2. 管理层及 DSH HTTP API 的分页、过滤、冲突裁决和审阅数据。
3. DSH 面板组件化、导航、列表筛选分页和审阅视图。
4. 全量测试、构建、手动 DSH 宽窄屏验证。
